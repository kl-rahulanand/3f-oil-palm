# AGENTS.md — 3oilpalm

## What this repo is

The 3F Oil Palm Financial MIS: a NestJS backend (`backend/`), a Next.js frontend (`frontend/`)
and a shared contract (`contract/`) over a Postgres app database and a separate Postgres
warehouse. SAP actuals and the client's budget workbook are ingested into the warehouse; a
code-authored semantic layer exposes Actual, Budget and % through the MIS statement, its
drill-down, the Excel export and the Ask assistant. Read-only against SAP and Smart Palm.

## Read before you change anything

1. `docs/product/BRIEF.md` — what the client asked for and what is out of scope.
2. `docs/specs/` — confirmed capability specs; `docs/decisions/` — accepted decisions (an
   accepted record wins over any note that drifts from it).
3. `docs/context/` — the client's own emails, workbooks and answers, verbatim.
4. `constitution/` — the coding, API, Swagger and exception-handling standards fresh code follows.
5. `docs/memory/` — durable project facts; `deployment/ec2/README.md` — the demo deployment.

## How the work runs

Forge drives every change from an approved story doc to a merged pull request; see the block
below and run `forge next` when unsure. Before delegating to subagents, read and follow
[ROLE.md](ROLE.md) for model selection, delegation scope, and escalation.

Non-negotiables that predate Forge v1 and still hold:
- Numbers are never fabricated: every figure on a surface traces to warehouse rows.
- The model selects from the governed vocabulary; it never authors SQL or joins.
- Fresh backend code follows the constitution; vendored Pulse code is covered by decision 0012.
- Tests are judged by the named leaf being present and executed, never by exit code alone.

## Working here with Forge

Forge takes each change from an approved plan to a merged pull request. Whenever you
are unsure, run `forge next`: it says where things stand and gives the exact next command.

If Forge started you with a brief, as a worker or a cold reader, that brief is your job: follow it
and nothing else.

### The shape of the work

1. A story starts as one short doc: `forge story new <KEY> "<title>"`.
2. It gets rounds of cold read (`forge read <KEY>`) until one finds nothing, then one approval
   from the human.
3. Each task runs in its own branch and worktree: `forge task start <KEY>/<TASK>`, then
   `forge work <KEY>/<TASK>`.
4. `forge close <item>` closes it when the tests pass and the review finds no serious problem.
5. The human merges unless the default branch's `forge.toml` has `merge = "agent"`.
   Then, once close says Ready, the agent runs `forge merge <item>`. After the story's last merge,
   `forge story done <KEY> "<outcome>"`.

### Smaller changes

- **Fix:** a small change, started with `forge fix start "<why>" --done "<done when>"`.
  Closed the same way, `forge close <FIX-ID>`.

### Rules

- Never commit directly to the default branch; every change goes through a pull request.
  `forge merge <item>` when the default branch allows it; `merge = "human"` is the default.
- Never edit the story doc after approval except through Forge.
- A task's brief is the contract; a worker that finds the brief wrong raises it, it does not
  reinterpret it.
- When a cold read or review names a problem, fix the problem; do not argue it down. What
  `forge next` names, unchanged, as the plan: from its title down to `## For the builders`, or the
  task section the brief names.
- Keep the worker's worktree clean of anything the task does not own.
- Run long `forge work` runs in the background and keep watching them.
