## Problem Statement

3F Oil Palm runs monthly management reporting (MIS) in Excel, hand-compiled by
one person (Srihari) from two systems: SAP (factory side) and the Smart Palm
SQL Server (farmer/plot side). The current process has four problems the client
named directly: data is not live, reports take significant time to prepare,
there is no clickable drill-down to verify how a number was derived, and the two
headline metrics — Yield per hectare and OER (Oil Extraction Rate) — are
distrusted because some input values are manually manipulated. The client wants
an automated, live MIS that reproduces the report, lets any number drill down to
its source, and adds a chatbot over the same centralized data.

## Demand Evidence

- Client ran a live demo of the current MIS + Smart Palm app, then signed an NDA
  specifically to proceed with this build. NDA-in-place is behavioral commitment,
  not just interest.
- The pain is concrete and quantified in kind: monthly manual compilation, no
  live data, no drill-down, and named distrust of Yield/ha and OER.
- Client explicitly asked for three deliverables (advanced drill-down report,
  live data, chatbot) and flagged budget tracking/alerting as a future want.
- Scale is real and growing: ~60,000 plots today, +6–7k plots/year.

## Status Quo

Srihari manually assembles an Excel MIS each cycle by pulling from SAP and the
Smart Palm SQL Server and stitching values together by hand. Cost: significant
preparation time per cycle, stale numbers by the time anyone reads them, and no
way to trace a figure back to the rows that produced it. Monthly targets are
tracked, but against hand-built actuals.

## Target User & Narrowest Wedge

**Users:** report consumers (management / CEO office, incl. Devanshi) who need to
verify how each monthly number was derived and track targets live; and the data
owner (Srihari) who today builds the Excel by hand.

**Wedge (client's chosen scope):** replace the full MIS report — automated, live,
with clickable drill-down — AND include the chatbot over the same data. This is a
*wide* wedge (every metric, both source systems, plus a second hard problem in
the chatbot). Recorded as the client's decision; the mitigation is to control the
PoC's depth (start with a representative slice of plots/one reporting period)
even though its breadth is the whole report.

## Constraints

- **Two upstream systems, read-only:** Smart Palm SQL Server + SAP. Access to
  both will be provided by the client. v1 never writes back to either.
- **Scale:** ~60k plots now, +6–7k/yr; metrics aggregate across many plots and
  factory batches. Live cross-system joins at this scale are a performance risk.
- **Live:** report must reflect source without manual recompilation. Exact
  freshness target (real-time vs near-real-time vs nightly) is an open question.
- **NDA in place:** data handling / residency / security posture to confirm.
- **Access control (financial data):** report and chatbot expose management-level
  financials under NDA. v1 must role-gate report access and scope chatbot queries;
  the chatbot answers only from the governed metrics, never free SQL over source.
- **History required:** monthly targets are tracked against actuals, so v1 must
  retain period-over-period snapshots (grain/retention TBD), not just a live view.
- **Metric definitions must be agreed with the client** before they are canonical
  — Yield/ha and OER formulas, aggregation unit, and time windows.

## Premises

1. **A read-only recompute-from-source MIS still reports distorted Yield/ha and
   OER, because the manipulation is upstream (inside Smart Palm/SAP).** —
   Client **disagreed** as a scope matter: the source-manipulation / accuracy
   problem is explicitly **out of scope for now**. v1 faithfully automates,
   goes live, and makes numbers traceable to source rows; it does not detect or
   correct upstream manipulation. Recorded as a deferral with a revisit trigger.
2. **A usable ground-truth to detect manipulation exists (audit trail /
   weighbridge / lab OER).** — Not pursued for v1 per premise 1. What we *do*
   have confirmed: Smart Palm SQL Server data access and SAP access.

**Honest framing (follows from premise 1):** v1 makes numbers *reproducible and
traceable to source rows*, not *verified correct*. Because the manipulation is
upstream, drill-down lands on the (possibly already-adjusted) source rows — it
shows how a number was built, which is exactly the client's stated "hard to
verify how/why" pain, but it does not by itself restore trust in Yield/ha and
OER. That distrust persists until manipulation is addressed in a later phase.

## Approaches Considered

### Approach A: Query direct + metrics layer (minimal)
Read-replica/direct queries against Smart Palm SQL + SAP. One semantic metrics
layer defines Yield/ha + OER once; dashboard renders them; drill-down queries
down to source rows on click; chatbot = natural language over the same metrics
layer. Fewest moving parts, fastest PoC. Risk: live joins across two systems at
60k plots can be slow and fragile; no historical snapshotting.

### Approach B: Warehouse + modeled metrics (ideal) — CHOSEN
ELT pulls both sources into a modeled analytics store (dimensions: plots,
farmers, factory batches; facts: harvest/receipt/extraction). Transformations
encode metric definitions with lineage; a BI/dashboard layer and drill-down sit
on top; the chatbot is grounded on the governed metrics. Scales to 60k+, gives
stable definitions both the report and the chatbot share, and sets up
budget/alerting later. Heavier PoC (needs the pipeline + store stood up).

### Approach C: Live Excel-shape shim (lateral)
Keep the exact report layout Srihari knows, back each cell with live queries +
drill-down links and a thin metrics layer. Lowest change-management friction,
fastest trust. Weaker as a reusable platform; chatbot bolted on separately.

## Recommended Approach

**Approach B — warehouse + modeled metrics.** At 60k plots growing 6–7k/year,
and with a chatbot that must answer with the *same* numbers the report shows, a
single modeled metrics layer with lineage is the core asset: it is simultaneously
what makes drill-down auditable, what grounds the chatbot, and what budget/
alerting will later read. A/C are faster to a demo but push the definitional work
downstream, where the report and chatbot would drift apart.

Pragmatic sequencing to respect "ship fast": stand up the pipeline + store for a
representative slice first (one reporting period / subset of plots), prove the
metrics-layer + drill-down + one report, then widen coverage. **The chatbot is in
v1 scope but sequenced as a fast-follow** after the report slice is trusted — it
reads the same governed metrics, so it cannot start before they exist.

**Drill-down is load-bearing and must be designed explicitly.** "Lineage" in the
transformation layer (metric → its inputs) is not the same as row-level
drill-*back* to SAP/Smart Palm rows. v1 must retain a raw/staging layer with
lineage keys so a clicked figure resolves to the specific source rows. Whether
the click hits the warehouse's retained rows or live-queries the source is an
open design question (below), but retaining raw rows is the safer default.

**Dashboard surface — build vs buy is open.** "BI/dashboard layer" above is a
role, not a product choice. Default assumption is a custom nestjs-react app (per
the harness stack) because the drill-down + chatbot are bespoke; a BI tool is a
possible alternative for the reporting surface. Decide in plan mode.

## Tech Stack Direction (draft — warehouse engine DECISION OPEN)

Reached through discussion 2026-08-14. **Not locked** — the warehouse-engine
choice is deliberately held open until the sample reports + a client cloud/
residency answer arrive.

- **Warehouse engine — OPEN.** Postgres-as-warehouse vs BigQuery. Postgres is the
  default for the PoC (snappy drill-down, in-harness, pgvector co-located,
  ~10–50M fact rows over 10 years is well within Postgres). BigQuery stays a live
  candidate for a company-wide platform trajectory. Decide when sample reports
  land and the client's cloud + NDA residency are known. Scale is *not* the
  decider at this volume.
- **Cube.dev — declined.** Not required. A single hand-built NestJS metrics
  module + Postgres materialized views gives one shared definition, drill-down,
  and snappy response without a new service. Revisit only if a genuine second
  consumer (a BI tool / second app) or cross-team metric governance appears.
- **Modeling/transform — dbt.** Staging → modeled star schema → rollups, with
  tests + lineage; handles both the one-time bulk backfill and incremental sync.
  Portable across the open engine choice (Postgres/BigQuery adapters). A thin
  SQL-migrations + materialized-views variant is the lighter fallback.
- **Metrics/serving — one NestJS metrics module** (+ matviews) that both the
  React report and the chatbot call. Single source of truth for Yield/ha + OER.
- **Ingestion — NestJS workers** (BullMQ) with `mssql` for Smart Palm + the
  agreed SAP export path. Two distinct paths: one-time bulk backfill (COPY) and
  ongoing incremental sync.
- **Reporting UI — custom React** (harness `apps/web`), grid + charts, drill-down.
- **Chatbot — Claude (latest) via tool-calling over the metrics module** + pgvector
  RAG. Answers *modeled metrics*, not open causal "why" questions — capability is
  bounded by the semantic model; set that expectation with the client.
- **History scope — PoC ingests a recent 1–2 year slice**; full 10-year backfill
  is a scheduled follow-on once the pipeline + metric definitions are validated.

## Open Questions

- **Exact definitions of Yield/ha and OER** — numerator/denominator, time window,
  and aggregation unit (plot / cluster / region / factory). These *are* the
  product; drill-down and chatbot both resolve to them.
- **SAP extraction mechanism — BLOCKING, needs a spike.** "SAP access provided"
  rarely means readily queryable. RFC/OData/BASIS enablement, licensing, and the
  actual export path are the single biggest hidden-complexity risk. Treat as a
  gating dependency with an early spike, not a background question.
- **Smart Palm access** — SQL Server read replica vs direct vs export.
- **"Live" freshness target gates the ELT design** — real-time implies CDC/
  streaming (materially harder); near-real-time/nightly implies batch ELT. Do not
  commit the pipeline design before this answer.
- **Drill-down mechanism** — retained raw rows in the warehouse vs live query back
  to source (see Recommended Approach).
- **Dashboard build vs buy** — custom nestjs-react app (default) vs a BI tool.
- **Plot dimension over time** — +6–7k plots/yr moves the population; need a
  slowly-changing plot dimension and a rule for period-over-period comparability
  and late-arriving/new plots in ELT.
- **Which report is v1** — one canonical MIS first, or several? Any other
  reports/dashboards in scope (Email 2 open ask).
- **Deployment / hosting / security** — on-prem vs cloud, data residency under NDA.
- **PoC depth boundary** — which plots / period is the representative first slice.

## Success Criteria

- The chosen MIS report is produced automatically from source with zero manual
  re-keying.
- Every reported figure (esp. Yield/ha and OER) is live and drills down to the
  SAP + Smart Palm source rows that produced it (traceable, not certified-correct
  — see Honest framing).
- Metric definitions are agreed with the client and computed in one place shared
  by the report and the chatbot.
- The chatbot answers questions over the centralized data using the same governed
  metrics (no divergent numbers), and refuses/handles gracefully questions the
  metrics layer cannot answer.
- ELT reconciles to source (row-count / control-total checks) so warehouse drift
  is detected, not silent.
- Access is role-gated and period history is retained for target tracking.
- Performance holds at representative scale (target slice of the 60k plots).
